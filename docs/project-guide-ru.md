# Путеводитель по проекту Printcartridge DB

Этот файл объясняет устройство проекта, назначение основных каталогов и файлов, а также показывает, куда вносить изменения для типовых задач.

## 1. Общая схема

Проект состоит из пяти основных частей:

1. **SQLite и доменная модель** — хранение производителей, принтеров, расходников, связей совместимости и доказательств.
2. **Импорт и экспорт** — проверка данных, нормализация, dry run и транзакционная запись.
3. **Сборщики официальных данных** — получение страниц производителей и формирование нейтральных JSON/CSV-файлов без прямой записи в базу.
4. **Локальный интерфейс** — React-клиент и HTTP API, доступные только через `127.0.0.1`.
5. **Windows-запуск и упаковка** — Electron-вариант и экспериментальный облегчённый .NET launcher.

Основной поток официальных данных:

```text
официальный сайт
    → src/collectors/*
    → data/official/* + .collector-state/*
    → строгий dry run
    → compatibility-importer.ts
    → database.ts
    → SQLite
    → web-server.ts / web/src/App.tsx
```

Сборщик никогда не должен писать непосредственно в пользовательскую SQLite. Сначала он создаёт проверяемый файл, после чего импорт запускается отдельным явным действием.

## 3. База данных и доменная модель (`src/`)

### `src/schema.ts`

Исходная SQL-схема. Основные таблицы:

- `manufacturers` — единый справочник производителей;
- `printers` — модели принтеров;
- `cartridges` — картриджи и более широкий каталог расходников;
- `data_sources` — источники данных;
- `printer_sources` — происхождение сведений о принтере без обязательной связи с картриджем;
- `compatibility` — уникальная связь «принтер ↔ расходник» и её итоговый статус;
- `compatibility_sources` — дополнительные источники и исходные значения для одной связи.

При добавлении полей миграции должны быть только аддитивными: существующие данные и доказательства нельзя уничтожать.

### `src/database.ts`

Главный класс `CartridgeDatabase`:

- открывает SQLite и включает foreign keys;
- создаёт схему и применяет безопасные миграции;
- перед важными миграциями создаёт резервную копию;
- выполняет CRUD для разрешённых таблиц;
- нормализует идентификаторы;
- идемпотентно записывает официальный `ImportRecord`;
- хранит доказательства и не понижает уже проверенные записи.

Если меняется способ записи в SQLite, начинать проверку следует именно с этого файла.

### `src/types.ts`

Минимальный общий контракт официального импорта: `ImportRecord`, допустимые типы картриджей, статусы проверки и результат валидации. Сборщики должны выдавать данные в этом формате.

### `src/normalize.ts`

Нормализует производителя, модель принтера и артикул картриджа для поиска дублей. Исходное отображаемое значение при этом сохраняется в базе.

### `src/coverage.ts`

Считает покрытие по производителям: сколько принтеров имеют связанные расходники, сколько остаются без связей и как изменились показатели относительно baseline.

## 4. Импорт, экспорт и пользовательские данные

### `src/importer.ts`

Базовый JSON/CSV-импорт формата `ImportRecord`. Сначала валидирует весь файл, затем записывает его одной транзакцией. Поддерживает `--dry-run`.

### `src/compatibility-importer.ts`

Строгий импорт официальной совместимости. Проверяет OEM-происхождение, тип `ink`/`toner`, точные доказательства, регион и статус. Неясные или недопустимые строки отклоняются либо отправляются на ручную проверку.

### `src/multi-source-import.ts`

Импорт CSV, TSV, XLS/XLSX и JSON из официальных, сторонних, открытых и ручных источников. Отделяет:

- категорию источника;
- надёжность утверждения;
- происхождение расходника (`oem`, `compatible`, `remanufactured`, `unknown`);
- тип расходника, включая бутылки, барабаны и прочие позиции.

Сторонняя запись не может автоматически стать официально проверенной.

### `src/exporter.ts`

Экспортирует базу в нейтральный JSON/CSV-формат.

### `src/desktop-data.ts`

Операции, которые использует локальный UI: ручной CRUD, preview/commit импорта, XLSX-экспорт, резервное копирование и безопасное восстановление SQLite.

### `src/cli.ts`

Командная строка проекта. Объединяет создание базы, импорт, dry run, экспорт, CRUD, статистику совместимости и отчёты покрытия.

Пример безопасной проверки:

```powershell
pnpm.cmd build:server
node dist/src/cli.js --db .\mvp.sqlite import:compatibility .\data\official\lexmark\lexmark.json --dry-run
```

## 5. Сборщики (`src/collectors/`)

| Файл | Что делает |
| --- | --- |
| `access-policy.ts` | Разбирает `robots.txt`, crawl delay, request rate и разрешённые окна посещения. |
| `page-collector.ts` | Общий resumable-движок: очередь URL, rate limit, retries, checkpoint, raw HTML, SHA-256, JSON/CSV и отчёт. |
| `kyocera.ts` | Сбор официальных моделей и тонеров Kyocera Europe. Имеет собственный исторически сложившийся цикл. |
| `epson.ts` | Консервативный сбор Epson с учётом разрешённого времени доступа и ручной проверки неоднозначных диапазонов. |
| `xerox.ts` | Проверяет официальные страницы Xerox, видимые данные и JSON-LD; исключает сторонние и некартриджные позиции. |
| `hp.ts` | Обрабатывает официальные страницы HP; неоднозначные семейства не превращает в verified-связи. |
| `lexmark.ts` | Находит принтеры Lexmark España по sitemap и читает только явные таблицы Return Program/Standard Cartridges. |

### `src/collector-jobs.ts`

Безопасный диспетчер сборщиков для UI:

- содержит фиксированный whitelist команд;
- не принимает произвольные shell-команды;
- разрешает только один процесс одновременно;
- сообщает состояние, checkpoint-прогресс, лог и ETA;
- останавливает активный процесс, сохраняя checkpoint;
- запускает импорт результата только отдельной командой.

### `src/brother-sitemap.ts`

Офлайн-импорт сохранённого sitemap Brother España. Создаёт только кандидаты принтеров и их provenance; наличие URL не считается доказательством совместимости.

## 6. Локальный API и интерфейс

### `src/web-server.ts`

HTTP API на `127.0.0.1`:

- поиск и статистика;
- CRUD принтеров, картриджей и связей;
- preview/commit импорта;
- экспорт, backup и restore;
- запуск, остановка, статус и импорт результатов сборщиков;
- раздача production-файлов из `web-dist/`.

Удалённого доступа и авторизации нет: сервер рассчитан на одного локального пользователя.

### `src/web-data.ts`

Read-модель интерфейса: SQL-запросы статистики, производителей, постраничного поиска и карточки принтера.

### `web/src/App.tsx`

Основной React-интерфейс. Здесь находятся поиск, карточка принтера, ручное редактирование, импорт, восстановление базы, справка и панель официальных сборщиков.

Файл сейчас крупный. При дальнейшем росте логично вынести диалоги и панель сборщиков в отдельные компоненты, сохранив существующий API-контракт.

### Остальные файлы `web/`

- `web/src/main.tsx` — подключает React к странице;
- `web/src/styles.css` — основная компоновка и стили;
- `web/src/pagination.css` — пагинация;
- `web/src/effects.css` — визуальные эффекты;
- `web/src/collectors.css` — дополнительные стили панели сборщиков;
- `web/src/ui-state.ts` — безопасное чтение истории поиска;
- `web/index.html` — HTML-точка входа;
- `web/public/favicon.svg` — иконка браузера.

## 7. Запуск и упаковка Windows

### `src/desktop-main.ts`

Electron launcher. Выбирает свободный локальный порт, запускает Node API, открывает системный браузер и создаёт tray-меню. Пользовательская база хранится в `%APPDATA%\PrinterDB`, а не рядом с EXE.

### `src/prepare-desktop-runtime.ts`

Копирует текущий `node.exe` в `desktop-runtime/` перед упаковкой portable-приложения.

### `launcher/PrinterDB.Launcher/`

Экспериментальный .NET 8 WinForms launcher без Electron. `Program.cs` управляет локальным сервером, браузером, single-instance и tray.

### `scripts/build-lightweight.ps1`

Собирает облегчённый folder-дистрибутив: .NET launcher, Node runtime, сервер, web-клиент, seed SQLite и необходимые native-модули.

## 9. Тесты

`tests/*.test.ts` сгруппированы по компонентам: база, импорт, UI, сборщики, восстановление, coverage и packaging-поведение. `tests/fixtures/` содержит только явно синтетические данные.

Основные правила:

- новый парсер должен иметь offline fixture;
- сетевой сайт не должен быть нужен для обычного тестового запуска;
- fixture нельзя импортировать в пользовательскую базу;
- для импортов проверяются dry run, идемпотентность и сохранение доказательств;
- перед завершением задачи запускаются typecheck, build и полный набор тестов.

```powershell
pnpm.cmd typecheck
pnpm.cmd build
pnpm.cmd test
```

## 11. Команды разработчика

```powershell
# Установка и проверки
pnpm.cmd install
pnpm.cmd typecheck
pnpm.cmd build
pnpm.cmd test

# Локальный интерфейс
pnpm.cmd mvp:seed
pnpm.cmd dev

# Production-подобный локальный запуск
pnpm.cmd build
pnpm.cmd web:start

# Статистика покрытия без изменения базы
node dist/src/cli.js --db .\mvp.sqlite coverage

# Сбор Lexmark небольшим resumable-пакетом
node dist/src/collectors/lexmark.js --output-dir data/official/lexmark --state .collector-state/lexmark.json --max-pages 50 --delay-ms 10000 --retries 2

# Проверка результата без записи
node dist/src/cli.js --db .\mvp.sqlite import:compatibility data/official/lexmark/lexmark.json --dry-run
```

## 12. Инварианты, которые нельзя нарушать

- Не создавать принтеры, картриджи или связи из предположений.
- `verified` требует явного официального доказательства точной пары.
- Не смешивать OEM, compatible и remanufactured.
- Не считать барабан, контейнер отходов, ремень или бутылку картриджем.
- Не обходить robots, авторизацию, bot protection и ограничения сайта.
- Не импортировать результат коллектора автоматически.
- Не удалять проверенные данные из-за их отсутствия в новом источнике.
- Не менять пользовательскую SQLite во время тестов или сбора.
- Хранить синтетические данные только в `tests/fixtures/`.

Если непонятно, где реализовать изменение, сначала определите его слой: **источник → нейтральный импорт → проверка → SQLite → API → UI**. Это помогает не помещать правила качества данных в визуальный компонент и не связывать сборщик напрямую с пользовательской базой.
